HOW IMAGES WORK NOW
Browser asks signUpload -> server checks auth() -> signs with
CLOUDINARY_API_SECRET -> browser uploads the file straight to Cloudinary
-> Cloudinary returns secure_url -> that URL is stored in the image field.
The secret never leaves the server. Validation is JPEG/PNG/WebP only,
max 5 MB, checked in the browser before upload.

next.config.ts allows remotePatterns for res.cloudinary.com and
placehold.co only. Every content <img> is now next/image using fill plus
a sizes prop, because user-supplied images have no known dimensions.

HOW PREVIEW WORKS
Public routes fetch with status PUBLISHED and hand rows to a View.
/admin/preview/[page] runs the same query without the status filter and
hands rows to the same View. Guarded by the existing proxy.ts matcher
/admin/((?!login).*) — no separate auth check was added.

DEFERRED DELIBERATELY
- CLOUDINARY_API_SECRET! uses a TypeScript non-null assertion. It
  silences the compiler without checking, so a missing key crashes
  confusingly at upload time instead of clearly at startup.
- No Cloudinary-side upload restrictions. Browser validation alone is
  bypassable by anyone technical.
- .env values are demo credentials and were exposed during Phase 4.
  Rotate all four before client handover: Neon password, AUTH_SECRET,
  Cloudinary key/secret, ADMIN_PASSWORD. Changing ADMIN_PASSWORD also
  needs the seed re-run, since the hash lives in the database.
- .claude/settings.json was committed by mistake; add .claude/ to
  .gitignore.
- pg SSL warning — forward-compatibility notice, no action.
- 6 npm audit vulnerabilities in build tooling. Do not run
  npm audit fix --force.
- Client cannot change their own password — deliberate, README note.
- Shareable secret-link preview for non-admins — future enhancement.
